# Python 相依掃描

在 F5 的 Extension Development Host 開啟側欄，先選「受測專案目錄」，再按欄位下方的「檢查此專案相依」。會直接檢查已選專案，不用再次挑選範圍；尚未選專案時，按鈕會先開啟資料夾選擇器。檢查結果顯示在同一區域。

要改查其他範圍，可按旁邊的「其他範圍…」，或從命令選單執行「檢查並補齊 Python 測試環境」：

- **整個專案**：使用側欄選定的專案；沒有設定時使用目前 workspace。多根 workspace 會再讓你選一個專案。
- **選擇資料夾**：遞迴掃描所選資料夾及子目錄。
- **單一 Python 檔案**：沿用側欄已選檔案，或開啟檔案選擇器；保留原有的隔離載入檢查與補裝流程。

最近使用的模式會排在選單第一項；專案、資料夾、Python 檔案與 requirements 分別保留上次選擇。取消選擇不會清除紀錄。

## 檢查及補裝

檢查後若需要補裝，會開啟「Python 相依安裝清單」頁面，先顯示：

- 安裝目標 Python 的完整路徑與是否為既有虛擬環境；不建立新的 `.venv`。
- 目前缺少的 import、對應安裝名稱／requirements 依據與使用位置。
- requirements 直接宣告的套件、版本、extras、平台條件標記與 constraint 來源；測試工具相依另外標示。
- 已預填的同名套件候選、無法完成清單的原因，以及只列出、不據此補裝的條件／可選缺項。

安裝名稱會自動帶入，通常直接按「確認並安裝」即可。名稱優先來自專案 requirements 或已保存的 `llmUnitTest.packageMappings`；兩者都沒有時，列出與 import 同名的候選，由 pip 嘗試安裝，無須逐項輸入。

同名只是候選，頁面會明示尚未驗證對應；不查詢套件索引來推測別名，也不把候選自動保存成明確映射。pip 找不到套件或安裝後仍缺少 import 時會停止並保留失敗，不會反覆改名重試。資料夾／專案模式重新檢查頂層套件位置，單檔模式重新做隔離載入；正式測試仍做完整模組預檢。

若已知安裝名稱不同，例如 import `PIL` 的套件是 `Pillow`，可在沒有 requirements 的清單直接修正：

1. 修改該列的 pip 套件名稱。
2. 按「儲存名稱並更新清單」。對應會保存到該專案的 `llmUnitTest.packageMappings`，其他既有對應會保留；沒有 workspace 時保存到使用者設定。
3. 確認更新後的清單並安裝。名稱格式有誤時會留在頁面，可直接修正。

保存名稱本身不會安裝套件；修改名稱後必須先更新清單，不能沿用修改前的安裝確認。保存後再取消，已保存的名稱會保留供下次使用。requirements 內的版本限制仍由原清單管理，不提供以名稱欄位覆蓋其宣告的操作。

按「確認並安裝」才會開始。按取消、關閉頁面或取消進度，不會安裝尚未批准的清單。所有項目已齊全時不會出現安裝確認。只有名稱格式無效、requirements 無法預覽等問題會阻擋確認；依頁面原因修正後重新檢查。

單檔載入可能只先發現第一個缺項；補裝後若出現新缺項，會再顯示新清單，取消時保留先前已完成的安裝。每次檢查都重新確認，不保存永久安裝授權。成功、失敗或取消後的 Markdown 報告都保留清單與確認狀態；確認不代表安裝或最終預檢已通過。

requirements 會保留原本的安裝語意，因此可能安裝間接相依或調整既有版本。此頁是直接宣告及已知缺項預覽，沒有先連線執行 pip dry-run，也不宣稱列出了最終所有版本。外部來源網址、憑證與任意清單原文不顯示。

本機 `-r`／`-c` 引用須在所選專案範圍內；工具引用須在工具清單所在目錄內。遠端、動態、循環、無法讀取或過大引用會阻擋安裝。可選擇涵蓋相依清單的專案根目錄，或調整為專案內清單。預覽最多追蹤 64 份清單、8 層引用與 1 MiB 內容；確認期間或安裝前檔案變更，須重新檢查並確認。

先檢查既有 Python，包括明確設定、專案虛擬環境及可取得的 Microsoft Python 環境資訊。使用者已設定 `llmUnitTest.pythonPath` 時，只檢查該 interpreter，不擅自換另一個。分析或模型資格測試執行中不能同時補裝。

資料夾模式只解析 Python AST，包含函式內的 import；依 Python 標準庫名單、專案模組位置與外部頂層套件位置分類，不執行來源程式，也不匯入外部套件。相同模組彙整所有使用位置及行號。

缺少必要外部套件時，從所選資料夾向上到所選專案根目錄尋找最近的 `requirements*.txt`，沿用既有選擇規則並列入安裝清單。沒有清單時，使用明確映射或同名候選。requirements 安裝後仍缺少時，要求補齊原清單，不繞過其版本限制。無清單逐項補裝仍有 20 次上限，避免反覆無效安裝。

每次補裝後重新檢查所選範圍，安裝完成後檢查相依版本及 coverage；成功才保存 Python。`if` 分支、捕捉 ImportError 的可選 import、TYPE_CHECKING import 的缺項另外列出，不單憑靜態掃描補裝。請依報告檢查實際需要的功能與平台；requirements 本身明確宣告的套件仍依清單安裝。

## 報告與限制

資料夾／專案掃描會開啟一份 Markdown 文件，成功與失敗都有報告，可自行儲存。內容包含首次缺項、最後掃描結果、準備是否完成、每個 import 的位置及分類。只保存模組名稱、相對路徑、行號與固定原因碼，不複製原始碼、provider 回覆或任意錯誤內容。

- 預設排除 `.venv`、`venv`、`env`、`.git`、`node_modules`、快取、build／dist、site-packages，以及有 `pyvenv.cfg` 的環境。設定的輸出子目錄及本工具版本化 run manifest 目錄也會略過。
- 不跟隨子目錄符號連結／junction；連結的 Python 檔案標為略過，不能當作已掃描。
- 單次最多 5,000 個檔案、累計 32 MiB 來源、單檔 2 MiB、10,000 筆 import 使用位置。語法錯誤、無法讀取、空範圍或超限會保留診斷，不能宣稱掃描成功；可改選較小資料夾。
- 專案 local／namespace／src 模組只依位置分類，沒有驗證其載入成功或所有成員存在。外部套件只檢查頂層存在，不證明子模組、版本、原生庫或執行期相依正確。
- 計算出的動態 import、別名或 plugin 載入不能靠 AST 全部列舉；報告提供常見動態 import 呼叫數。條件分支只保留條件分類，不猜測是否會執行。
- 只掃描所選範圍，不追蹤範圍外來源或自動合併多個子專案 requirements。不同子專案可分別選資料夾檢查。

「靜態相依檢查完成」不等於整個應用能執行。正式測試仍在模型請求前進行模組隔離載入與 coverage 預檢；初始化副作用、子模組或版本錯誤仍照原分類回報。
