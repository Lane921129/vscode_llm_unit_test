# CI 與車輛小批次修復

## 原批次證據

`vehicle_manageme_2026_10_11_16_30` 共選取 212 個目標；停止時 106 個已有終態，另 106 個待執行。主要失敗為 Analyst 契約無效（82）、模型請求前提示超額（17）、審查提示超額（2）及 Writer 逾時（2）。沒有實際 Reviewer 請求或突變量測。

200 次邏輯請求中 197 次完成、2 次逾時、1 次取消，沒有 HTTP 500。183 次 Analyst 請求中 182 次完成，173 次回覆無效；首次無效 91 次中補正救回 9 次，82 次仍失敗。173 次無效回覆的長度 214 與摘要完全等於公開 system prompt 的單行 JSON 範本，證明存在範本回聲。沒有保存或公開完整 provider 回覆。

同期 import check 的 7 個模組均可載入；隔離計畫包含 18 個資料表、98 欄與 5 項資源，737 個生命週期均回收。這批主要瓶頸已經不是缺套件或要求再次初始化。

## 修正與因果界線

1. **CI**：Windows 的 Node 非 native realpath 與 Python 實體長路徑不一致；Ubuntu 的歷史 coverage 解析誤處理 Windows 分隔符號。改用既存來源的實體身分，並補真正 8.3 路徑、連結與 UNC 負例。資源批准仍獨立驗證，不以實體化原資源來解決路徑問題。
2. **Analyst**：移除可照抄的完整 JSON 範本，依具體失敗類型提供固定補正指引。解析門檻、一次補正及共同期限不變。
3. **提示容量**：原模組 import 44 筆／5,465 字元被整份帶入小函式；caller 的完整 transport 與狀態樹也重複進入 Reviewer。改為保守的相關 import 與既有呼叫投影，完整必要證據不截斷。自動輸入預算與實際 wire context 對齊。
4. **分治合併**：保留已通過基線的 class 與方法身分，避免合併器改名後被成功案例保護 gate 拒絕，進而浪費 Writer 請求。
5. **Trace 時間分配**：車輛模組獨立重跑規劃仍需約 4.4 秒，每個案例卻只有 2 秒可重新啟動並匯入，造成零觀測。成功規劃的耗時加入單案例上限作啟動成本估量，原總期限不增加；實際分配、timeout 與未啟動案例分別記錄。規劃失敗不校準，案例間仍為獨立程序。

因此這批失敗不能只歸因於模型參數量。先前為小模型精簡 Analyst 契約時加入的可抄範本，確實參與這次失敗；提示投影與預算接線也有實作問題。13B 並不會自動消除這些流程缺陷，但目前證據也不能證明修正後所有模型回覆都一定正確。

## 真實模型驗證範圍

開發機實際可用模型為 `qwen2.5-coder:3b-instruct` 與 `codegemma:2b`。本次採已通過固定 Writer 真實執行與 Reviewer 契約資格的 Qwen 3B／16,384 context、temperature 0，以正式命令和既有批准的隔離計畫驗證；未下載或假冒實驗室 Codellama 13B。

公開中性 increment 的舊／新 Analyst 提示各執行一次，兩者均回傳可解析計畫。這一組沒有重現舊範本回聲，所以只能證明新提示可運作，不能計算 Codellama 的改善率。

第一個車輛函式 `get_vehicle_status_map` 已走完 Analyst、Writer、真實執行、Reviewer 核准和 Mutatest 3.1.0。選定函式覆蓋率 2／2；引擎沒有可用突變候選，終態為 `no-mutation-candidates`，分數為空而不是 100%，不是完整品質通過。21 個隔離租約均回收，來源與依賴未變；沒有寫入使用者設定或存取 SecretStorage。後續修正仍須另以最終版本驗證。

上述執行的來源與相依摘要皆不變，SecretStorage 存取與設定寫入皆為 0。日期例外規則無條件要求 `side_effect` 是額外提示偏導，已改為條件式，並補純標準庫真輸入及參數 setup 指引；這些後續提示改動需要另行驗證，不能把前述執行套用成新版本成果。

提示修正後再次實測，仍不能宣稱已解決所有候選問題：

- `format_duration_text`（`ZkyGOh`）：6 次請求皆完成，提示最大估量 5,947／11,468。Tier2 仍使用錯誤的日期模組 patch；Tier1 已移除 mock，卻缺少目標 import。Trace 規劃 4.40 秒、4 timeout、6 未啟動，因此追加前述時間分配修正。
- `can_edit`（`scnkLN`）：7 次請求皆完成。Tier2 改為直接傳參數，但把需具備 attribute 的物件寫成 dict，5 個測試中 3 通過、2 assertion 失敗；Tier1 又回到不存在的模組屬性 patch。兩個唯一候選、四次重複，未進入 Reviewer／突變。唯一 Trace 案例為 `unsupported-input-snapshot`，沒有可採用的已驗證結果。

這些剩餘失敗是實際候選錯誤，不是把有效測試誤擋；小模型的候選品質仍有限，不能將所有後續失敗都歸因於提示或僅憑參數量保證成功。

Trace 時間修正後的 `format_duration_text`（`jBalYK`）取得第一筆正常觀測：規劃 4.765 秒，案例有效上限 6.765 秒，首例 4.773 秒完成。第二例僅剩 2.458 秒而逾時、其餘 8 例未啟動，總約 12.035 秒；`complete=false` 保留，不能說 10 個案例全數完成。Writer 確實收到該筆觀測，但仍產出缺少 import／錯誤 patch 的候選並原樣重複，未進 Reviewer／突變。6 次請求皆完成，16 個租約回收。

另開明確選用 **builtin** 的對照（`NYvzHX`），`get_vehicle_status_map` 已完整通過：4 次模型請求全部完成，Analyst、Writer、真實執行及 Reviewer 核准後，`builtin-ast-v2` 的 11 個唯一突變全部執行且 KILLED，沒有 timeout／error／未執行；目標覆蓋 2／2。來源、測試、run、ReviewApproval 與量測身分一致，scorecard 重新核對仍為 `fullyPassed=true`，21 個租約回收。這不是 Mutatest 的自動 fallback，不改寫原零候選結果，也不代表另兩個失敗目標或 212 目標全批通過。

此次核驗也發現頂層 journal 的 `mutationStatus` 停留在初始值，但 quality checkpoint、正式報告及 scorecard 均讀取完整量測證據，因此判定沒有被誤升級。後續只修正成功保存時的欄位同步，另以正式流程與審查未完成整合測試驗證；可執行 checkpoint 的「突變尚未量測」歷史狀態維持不變。

## 實驗室驗證

1. 在 `lane_edition` 拉取本次提交後重新 F5；選取既有車輛專案與原隔離計畫，先核對環境檢查就緒，不重複安裝或重新初始化已就緒的項目。
2. 保留 `full`、Tier2、5 次迴圈及原突變引擎；先選上述少量目標，暫不以 212 個目標消耗模型時間。
3. 檢查模型連線取得的 context metadata。若工具確認模型支援 16,384，可明確設定 `llmUnitTest.runtimeContextTokens=16384` 並重新測試連線，使各角色資格與實際容量相符。未知或不足的 metadata 不應強行通過；較大 context 也可能增加 GPU／CPU 負擔。
4. 分別核對 Analyst 是否首次有效、完整提示有無超額、候選實際執行、同候選 Reviewer 核准、引擎身分及突變候選數。`no-mutation-candidates` 不是突變 100%；builtin 與 Mutatest 的算子不同，對照結果需分開記錄。
5. 保存每個函式的 `final_report.md`、`failure_report.md` 與 `loop`；連同 `run_manifest.json`、`role_events.jsonl`、`function_knowledge.json` 分類後再擴大批次。Codellama 13B 尚需在實驗室實測，不能以本機 Qwen 結果替代。
