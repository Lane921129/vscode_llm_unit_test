## 主要失敗分類與具體原因

共 445 次候選拒絕；這些是候選事件次數，會在同一目標重複發生，不能相加當成失敗函式數。

| 候選拒絕代碼 | 次數 | 本批意義 |
| --- | ---: | --- |
| `candidate-structure-rejected` | 188 | 缺 target import、替換受測目標、無 assertion、無法證明 mock assertion 綁定、非隔離 SQLite 等多種契約問題 |
| `repeated-candidate` | 114 | 修訂送回已嘗試的相同候選，沒有實際消除錯誤 |

| `import-binding-changed` | 2 | 改變既有受測目標綁定 |

### 1. 基本綁定仍常失敗

`get_app_dir` 的原候選與修訂都呼叫未定義的目標；`_now_text` 也未明確匯入受測函式。這類問題不能透過更多業務測資解決，應將 canonical target import、可 patch 的 use point 與測試 helper 綁定做成簡短、確定的輸出骨架，讓模型填案例與 assertion；仍由 AST 和隔離執行驗證骨架未被破壞。

證據：`config_b79606fb/get_app_dir_09b9a9a6/loop/_run/role_events.jsonl:47,63-64`；`database_3549b002/_now_text_5477bd02/failure_report.md:6`。

### 2. Mock 問題包含「mock 錯對象」與「預期錯契約」

`_table_columns` 的拒絕候選直接使用 `@patch('database._table_columns')`，把正在測試的目標當成 mock。這不是單純 JSON／純文字格式問題；不能移除禁止替換受測目標的 gate 來換取通過。

`_connect` 的 assertion 預期把 `WindowsPath` 傳給 `connect`，實際函式傳入字串，因此執行失敗。`init_db` 則預期 `cursor.execute` 只呼叫一次，實際為 41 次。後續修訂仍重複相同候選。這說明目前的依賴名稱、參數型別／序列、Mock 回傳結構和呼叫次數，未被有效轉成 Writer 能遵守的窄契約。

改善應優先提供已確認的 mock 邊界與可觀察行為，不要任意要求所有 DB 呼叫必須一次，也不要從未知執行紀錄猜出預期答案。宿主結構 gate 對「無法證明綁定」的拒絕仍須逐案例檢查是否過度保守；此批的拒絕總數不能全部宣稱為模型幻覺。

證據：`database_3549b002/_table_columns_09aaedf2/loop/_run/rejected_candidates/candidate_64e3ea338f0bee09ab610892f52dd6f09c68969f9b7f2f6d80804d74c28bf1a4.py:6`；`database_3549b002/_connect_7b97d641/loop/_run/role_events.jsonl:58,75,92`；`database_3549b002/init_db_e9dcae54/loop/_run/role_events.jsonl:61,80,99`。

### 3. 已經能跑的測試，常無法有效提升突變分數

23 個目標保留基線但未達標，其中 19 個最終分類為 `quality-stagnation`，另 4 個在新增／修訂候選驗證失敗後保留舊基線。例如 `get_vehicles` 突變分數 20%；刪除 SQL 執行等變異仍能存活，顯示只檢查固定 Mock 回傳值無法充分保護真正依賴行為。

本批 27 次 `quality-experiment/unsupported` 全為 `instance-target-required`：現有實驗工具未覆蓋這批需要補強的模組層函式。27 次 Analyst quality 的實測引導陣列也都是空的。此時再要求 Writer「多加案例」容易得到同樣測試或重複輸入。

下一步應讓缺口引導支援已知模組層 DB use point，把「哪個呼叫被刪除仍存活、哪些參數／交易行為未被觀察」轉成可核實的小任務；未知需求須標示需人工補充，不能用模型猜測填成 assertion oracle。先對 `get_vehicles`、`get_destinations` 做小批次，確認增加的 assertion 確實殺死指定變異，再擴大範圍。

證據：`database_3549b002/get_vehicles_c5029ff6/loop/_run/role_events.jsonl:89,93,107,170,175,189`。這是工程能力的覆蓋缺口，不是「所有函式都不可能迭代改善」的證據。

## 設想是否過於理想，以及接下來的改善順序

**閉環設計可行；「任意 Python 專案、零人工輸入、每函式必達標」則不是目前可保證的契約。**Python 專案可能依賴硬體、帳號、網路、資料庫狀態、互動 UI 或未寫明的業務需求。AST 與呼叫站描述程式結構，Trace 描述特定輸入下的觀測，另一個 LLM 提供審查意見；三者都不能憑空產生外部業務正確性的權威答案。

相關研究也採取執行與覆蓋回饋迭代，並非單靠一次提示：[CoverUp](https://arxiv.org/abs/2403.16218) 支持這類閉環工程方向。[另一項關於生成測試與程式缺陷的研究](https://arxiv.org/abs/2412.14137) 說明只追求測試在現有程式上通過，可能將既有 bug 固化成預期結果。這些研究不代表本專案已驗收，也不是小模型或任意專案成功率的保證。

建議依序處理：

1. **先確認執行的是新建置，且中止能真正停止工作。**在發送任何新請求之前綁定 run ID；中止後不排程下一目標。保留原因、pending 目標與必要清理紀錄。
2. **縮小重測範圍但維持品質門檻。**由使用者選定主要版本，先測 `get_app_dir`、`_connect`、`_table_columns`、`get_vehicles` 及一個 UI 函式；避免同時測副本與備份 215 次，讓每次修復可比較。
3. **先修固定骨架與 Mock 契約。**固定 target import／不可 patch 目標／可 patch 依賴清單；對名稱、參數型別、cursor row、交易呼叫提供短且可核實的契約。重複候選不再耗用相同修訂路徑。
4. **補齊模組層品質缺口的可執行引導。**先讓一個已通過基線的 DB 函式，針對指定存活變異產生有效 assertion，再擴展到其他函式。未具備 oracle 時明確要求需求或 fixture，不宣稱自動補強成功。
5. **最後比較模型與輸出額度。**用同來源、同範圍、同設定比較目前 3B 與實驗室可用模型。分開記錄輸出截斷、候選通過率、品質補強增益與總耗時；不要以參數量推定一定成功，也不要一律延長 timeout 或加長 prompt。

可作為收尾目標的是：對具備明確依賴邊界與需求的 Python 函式，閉環能成功或給出可操作的受阻原因，使用者能立即中止，且任何未驗證結果都不冒充通過。這仍符合原先 AI 分工與突變迭代的構想，同時能用這批實際數據驗收。
