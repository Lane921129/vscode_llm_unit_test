## 0. 執行規則

### 0.1 使用者在 2026-11-04 的決策（優先於 `PROJECT_RULES.md` 中衝突的舊條款）

1. **單一生成流程，預期值以規格為準。** 不做錯誤定位。每個案例的預期值，在有規格來源時由模型依規格預測；與實際執行結果不一致時，不採用實際結果，改列入「規格不符清單」（第 1 節）。原本規劃的兩種模式已經合併。

## 1. 目標

### 1.1 單一流程：預期值以規格為準

| 項目 | 說明 |
| --- | --- |
| 目的 | 產生單元測試與突變測試；確保預期值來自規格，而不是程式現在的行為，避免把 bug 寫成正確答案 |
| 不做 | 錯誤定位（指出 bug 所在的程式行） |
| 預期值來源 | 有規格時用 `spec`（模型依規格預測）；沒有規格時用 `observed`（實際執行結果，並標示「未經規格確認」） |
| 規格來源 | docstring、型別註記、使用者需求檔（`llmUnitTest.requirementsFile`）、README 中對應的說明。函式名稱只能作為弱依據 |
| 主要產出 | 正式測試檔（全部通過，用於覆蓋率與突變測試）、`test_spec_mismatch.py`（以規格值撰寫、目前會失敗的測試）、`spec_mismatch.md/json`、需求涵蓋表、設計疑點清單 |
| 成功指標 | 可用率、高品質率、突變分數；規格不符的偵測率與誤報率；與對照組比較「bug 被寫成正確答案」的比例 |

新增設定 `llmUnitTest.specOracle: "auto" | "off"`，預設 `auto`：有規格來源時啟用規格預測，沒有時退回 observed。`off` 等同舊行為，用於對照與除錯。側欄要能切換。

### 1.2 分層成功（目標層級）

| 終態 | 條件 |
| --- | --- |
| `quality-passed` | 「可用」的所有條件，加上 Reviewer 無阻擋意見，且覆蓋率與突變達到品質門檻 |
| `usable` | 正式測試檔中至少一個測試方法在隔離環境執行通過、確實呼叫真實目標，並完成突變量測，分數照實記錄 |
| `failed` | 正式測試檔中沒有任何可執行且通過的測試 |
| `environment-blocked` / `tool-blocked` | 沿用現有分類，不計入模型失敗 |

規格不符的列不放進正式測試檔，所以不影響目標層級；數量另外統計並列入報告。舊終態 `passed` 對應 `quality-passed`，`retained-after-failure` 對應 `usable`。

### 1.3 規格預測的分級

| 狀況 | 狀態 | 處理方式 |
| --- | --- | --- |
| k 次預測一致，且與實際結果相同 | `spec-matched` | 寫進正式測試，預期值來源標為 `spec` |
| k 次預測一致、與實際不同，且 `basis` 引用的文字確實存在於規格來源 | `spec-mismatch` | **不寫進正式測試**；以規格值寫進 `test_spec_mismatch.py`，並列入報告 |
| k 次預測一致、與實際不同，但 `basis` 找不到出處，或只依據函式名稱 | `needs-review` | 正式測試採用實際結果，標示「未經規格確認」；同時列入報告的「需人工確認」 |
| k 次預測不一致 | `prediction-unstable` | 視同沒有規格，採用實際結果，標示「未經規格確認」 |
| 沒有規格來源，或 `specOracle=off` | `observed-unconfirmed` | 採用實際結果，標示「未經規格確認」 |

k 預設為 3，可在設定中調整。

## 2. 架構總覽

v2 流程以**案例表（case table）**作為角色之間唯一的溝通媒介。每一列是一個測試情境，一列失敗只影響那一列。

```
原始碼＋AST／相依事實＋需求清單
        │
        ▼
[Analyst-情境] 產生案例列（情境、輸入、相依行為），每行一個 JSON 物件
        │
        ▼
[程式] 逐列驗證 ──無效列──▶ 記錄原因後丟棄
        │
        ├─ 有規格來源 ─▶ [Analyst-規格] 只看簽名、docstring、型別註記、需求清單，
        │                 為每列預測 expect 與 basis，獨立詢問 k 次
        │                 （提示中不含函式本體與任何執行結果）
        ▼
[程式] Capture run：依該列 patch 相依，在隔離環境呼叫目標，記錄 actual
        │
        ▼
[程式] 依 1.3 節比對與分級
   ├─ spec-matched ──────────────▶ 正式測試（預期值＝規格）
   ├─ spec-mismatch ─────────────▶ test_spec_mismatch.py＋規格不符報告
   └─ needs-review／unstable／無規格 ─▶ 正式測試（預期值＝實際，標示未經規格確認）
        │
        ▼
[Reviewer] 只看案例表：建議新增列、標記可疑列（不阻擋 usable）
        │
        ▼
[程式] 依列產生測試方法；只有 needs-setup 的列才請 [Writer] 撰寫 setup
        │
        ▼
[程式] 逐方法執行 ──失敗方法──▶ [Bug Fixer] 只修那一個方法（不可修改預期值）
        │
        ▼
合併正式測試 → 覆蓋率 → 突變測試
        │
        ▼
[Quality Analyst] 一個存活突變 → 一列新案例 → 回到規格預測與 capture
        │
        ▼
報告：測試檔、分數、規格不符清單、需人工確認清單、需求涵蓋表、設計疑點
```

Analyst-情境 與 Analyst-規格 是同一個角色、兩份不同的提示，不新增模型角色。情境階段要看程式碼，才能涵蓋所有分支；規格階段刻意不看程式碼，避免模型照著有 bug 的實作算出答案。

## 3. 核心資料結構：`case-table-v1`

### 3.1 模型輸出格式（給小模型看的格式）

**每行一個扁平 JSON 物件**，不要包成陣列。程式逐行解析，壞掉的行只影響自己。

**Analyst-情境**的輸出：

```json
{"scenario":"BMI 剛好 18.5 為健康下界","category":"boundary","args":"(18.5, 100)","kwargs":"{}","mocks":"","requirement":"R2"}
{"scenario":"查無車輛","category":"dependency-failure","args":"(999,)","kwargs":"{}","mocks":"db.fetchone -> None","requirement":""}
```

**Analyst-規格**的輸出（程式提供列的 id、情境與輸入，模型只填預期與依據）：

```json
{"id":"C1","expect":"return (18.5, '健康體位')","basis":"docstring: 18.5 <= BMI < 24 為健康體位"}
{"id":"C2","expect":"raise ValueError","basis":"R3: 身高為 0 時拋出 ValueError"}
```

欄位規則：

| 欄位 | 說明 | 程式如何驗證 |
| --- | --- | --- |
| `scenario` | 80 字以內，之後當作測試方法名稱和註解的來源 | 長度、非空 |
| `category` | `normal` / `boundary` / `error` / `dependency-failure` / `state` 其中之一 | 列舉值 |
| `args` | Python tuple 字面值 | `ast.literal_eval`，並與目標簽名做 `inspect.signature().bind` 比對 |
| `kwargs` | Python dict 字面值 | 同上 |
| `mocks` | 以 `;` 分隔，每段為 `相依名稱 -> 字面值` 或 `相依名稱 -> raise 例外名稱` | 相依名稱必須存在於 AST 提供的相依清單；值以 `ast.literal_eval` 解析 |
| `requirement` | 需求編號，例如 `R2`，可空 | 必須存在於需求清單 |
| `expect`（規格） | `return <字面值>` 或 `raise <例外名稱>` | 解析 |
| `basis`（規格） | 引用的規格文字 | 程式檢查引用文字是否真的出現在規格來源中；只依據函式名稱時標為弱依據 |

不能用字面值表達的輸入（例如需要建構物件），`args` 寫成 `"<needs-setup: 說明>"`，交給 Writer 只為這一列撰寫 setup。

### 3.2 程式內部結構

```ts
// src/pipeline/caseTable/caseTable.ts
export type CaseCategory = 'normal' | 'boundary' | 'error' | 'dependency-failure' | 'state';
export type ExpectedSource = 'spec' | 'observed';

export interface CaseRow {
    id: string;                       // host 指派：C1, C2...
    origin: 'analyst' | 'reviewer' | 'quality-analyst';
    scenario: string;
    category: CaseCategory;
    call: { args: string; kwargs: string } | { needsSetup: string };
    mocks: { dependency: string; behavior: 'return' | 'raise'; value: string }[];
    requirementId?: string;
    predictions?: { kind: 'return' | 'raise'; value: string; basis: string; basisVerified: boolean }[];
    actual?: { kind: 'return' | 'raise'; value: string };
    expected?: { kind: 'return' | 'raise'; value: string; source: ExpectedSource; confirmedBySpec: boolean };
    oracleStatus?: 'spec-matched' | 'spec-mismatch' | 'needs-review' | 'prediction-unstable' | 'observed-unconfirmed';
    status: 'proposed' | 'invalid' | 'captured' | 'capture-failed'
        | 'test-generated' | 'test-passed' | 'test-failed';
    reason?: string;                  // 無效或失敗的原因碼
    testMethod?: string;              // 產生的方法名稱
}
```

`case_table.json` 保存在每個目標的結果資料夾，報告與 Webview 直接讀取它。

### 3.3 比對規則

- 回傳值：兩邊都用 `ast.literal_eval` 解析後比較。浮點數用 `math.isclose(rel_tol=1e-9, abs_tol=1e-12)`；tuple、list、dict 遞迴比對。
- 例外：比較例外類別名稱，包含 MRO 中的父類別名稱；例外訊息不比對。
- 實際結果無法解析成字面值時，標為 `observed-unconfirmed`，不列為規格不符。

## 5. 提示詞原則（v2 所有角色共用）

- 每個提示只有一個任務，最後一句是輸出格式，並附**一個**範例輸出。
- 不在提示中描述內部契約名稱、hash、版本或驗證機制；這些由程式處理。
- 輸出長度上限要明確寫出，例如「最多 8 行」「只輸出一個 Python 方法」。
- 模型回覆格式錯誤時，**只針對錯誤的那一行**重問一次；仍錯就丟棄該列，不重問整份。
- **Analyst-規格的提示不得包含函式本體、執行觀察值、trace、覆蓋率或突變結果，也不得出現「已驗證」說法。** 新增測試 `specPromptBlindness.test.ts`，掃描實際產生的提示並斷言這點。
- 品質模式 Reviewer 的「已驗證回傳值」說明（050f969 的提示）只能用於 Reviewer，不能出現在 Analyst-規格的提示中。

抽樣清單寫死在檔案中。報告要把「有規格來源」與「沒有規格來源」的函式分開統計。

### 6.2 模型篩選（第 1 週）

- 從附錄 A 選 4～6 個模型，用**相同的** `num_ctx`（8192）、溫度與設定，對評估集中 20 個固定目標（BMI 全部、validators 6 個、車輛 8 個、bottle 6 個）跑 v1 流程。
- `python_scripts/eval_aggregate.py`：讀取多個批次的 `batch_manifest.json`，輸出每個模型的可用率、高品質率、平均突變分數、角色回覆可用率、平均耗時。
- 選出最好的 1 個為主力模型、1 個為備援；之後所有開發驗證都用主力模型。

### 6.3 對照組

- `python_scripts/eval_baseline_plain_llm.py`：對同一批目標，用同一個模型發出**單次**請求：「以下是一個 Python 函式，請為它寫 unittest」，附完整函式原始碼。不修訂、不審查、不給 AST 與執行結果。
- 產生的測試放進與本系統相同的隔離環境執行，用相同的覆蓋率與突變工具量測。跑不起來的也計入分母。
- 選配對照組 B：失敗時把錯誤訊息回給模型，最多重試 3 次，用來區分效果來自「重試」還是來自「架構」。

### 6.4 埋 bug 評估

- `eval/seeded_bugs/`：人工撰寫 15～20 個 bug，每個是一份 patch 加上中繼資料（目標函式、類型、說明）。類型分布：邊界運算子、單位或換算、漏處理的例外、錯誤的預設值、回傳錯欄位、條件反向。**不要直接用突變運算子產生**，要像真實的人為錯誤。
- 被測函式必須有 docstring 或需求檔描述正確行為；原本沒有的，可以在評估副本中補上說明，並記錄為評估設定的一部分。
- `python_scripts/eval_seeded_bugs.py`：每次只套用一個 bug 到複製出的專案，分別跑本系統與對照組，記錄三個指標：
  1. **偵測率**：本系統把該 bug 對應的情境列為 `spec-mismatch`（以及加上 `needs-review` 後）的比例。
  2. **bug 被寫成正確答案的比例**：正式測試檔在有 bug 的程式上全部通過、且斷言了錯誤行為的比例。本系統和對照組都要量，這是主要的比較指標。
  3. **誤報**：在未埋 bug 的乾淨版本上，每個函式的 `spec-mismatch` 平均數。

### 6.5 最終報告（第 3 週）

主力模型對評估集跑 3 次，每個指標報中位數與範圍；所有失敗、逾時、未執行都計入分母。本系統、對照組 A、（選配）對照組 B 並列比較。
