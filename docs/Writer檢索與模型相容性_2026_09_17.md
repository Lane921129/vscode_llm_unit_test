# Writer 檢索與模型相容性

本輪先以實驗室 `codellama:13b` 穩定完成五類小批次為驗收目標；1B～5B 是後續實測目標。程式依參數量與 context 能力資料選擇提示，不以模型或 provider 名稱設定例外。參數量與單元測試通過都不能證明某個模型已達到品質門檻。

## 改動依據

2026-09-17 最新批次分析 snapshot 中，285 份一般 manifest 有 208 份環境失敗（127 缺模組、81 載入副作用被擋），這些目標沒有送出 Writer 請求。到達分析階段的 75 個目標，其既有跨檔依賴清單皆為空；這是補同模組 helper 檢索的依據，不代表 75 個目標都有 helper。中性案例另重現 `setUp` 建立 Mock、以及 `patch(return_value=...)` 的合法呼叫斷言遭 gate 拒絕。Reviewer 的無效回覆則常缺少精確引述、具體 reason/action，或超過五項。

本輪不安裝或執行原私有應用，不把缺相依或載入副作用改判成功，不以更換模型或放寬 gate 處理上述環境失敗。

## 實作

1. `ast_extractor.py` 以真正未被區域名稱遮蔽的呼叫，查找同模組未裝飾、未重綁定的頂層 helper。廣度優先、最深兩層、最多六個、函式來源合計最多 12,000 字元。保留完整函式與必要全域定義、來源雜湊及省略清單；不執行 helper、不製造 Trace。循環會去重；未知、動態屬性呼叫及歧義綁定保留未知。原有可解析跨檔依賴與 caller 探索仍保留。同檔 helper 的有效性由整個目標檔的來源版本檢查涵蓋。
2. `compact-writer-v1` 用在小模型策略的正式 Writer evidence bundle。保留目標全文、qualified binding、完整建構與 module setup、caller 專屬 Trace、相依實測事實、規則與既有通過測試。規則不再重複附加同一批推導說明。先加入完整相依來源，再選少量範例，最後才放可省略的分析假設。任何片段都不切半，也不把 dependency 的 return expression 當 oracle。舊 large 提示的 dependency 摘要同樣改為整段保留或明示省略。
3. 五種中性 Writer 範例：SQLite context manager、AsyncMock、instance constructor、patch scope cleanup、受控 side_effect。依 AST 的 async、class、imports、calls 等特徵最多取兩例，預算不足時整例省略。範例在回歸中真正執行 unittest，SQLite 例不建立實體資料庫。它們教導 setup 寫法，不是目標輸出規格；未索引失敗候選或私有原始碼。
4. Mock gate 接受可證明的直接 `setUp` 實例屬性和設定 `return_value` 的 patch 本身之呼叫斷言。仍拒絕無關 Mock、未執行分支、假物件、重綁定、假 assertion 方法、被改寫的 target 與未 await 的 async 呼叫。literal return_value 的子屬性不能冒充 Mock。複雜繼承、decorator、descriptor、asyncSetUp 和未知控制流程維持保守；成功仍須實際隔離執行。
5. Reviewer 保留 review-v4 和完整測試原文要求。Ollama 請求使用 bounded JSON Schema；不支援 schema 的伺服器沿原請求 deadline 回退文字。每陣列最多五項，合計五項與精確引述、actionable reason/action 仍由 parser 驗證。拒絕記錄穩定代碼，例如 `too-many-findings`、`excerpt-not-in-test`，不把無法解析當空問題通過。
6. 參數量解析區分 M/B，未知或標有名稱推定的數值不視為精確參數量。已知 ≤13B、Tier 1/2 保持 small 提示，即使 advertised context 很長。完整角色請求包含 system/output contract 都必須先符合輸入預算；超出時標記 `prompt-budget`，不發送、不截斷真實證據。Ollama 明確收到對應 `options.num_ctx`，各角色使用同一個 context 設定，並保留約 30% 給輸出。這是字元估計，並非精確 tokenizer 或 GPU 記憶體量測。

`Semantic Analyzer` 仍是分析角色；本輪新增的是它與 Writer 前端的符號檢索。這屬於結構化檢索增強，不需要向量資料庫。尚未擴展成任意 repo 的跨檔多跳檢索，也未導入以失敗模型產物訓練的案例庫。

## 實驗室驗收

1. pull `lane_edition`，重新啟動 Extension Development Host，使用原 workspace `.venv`。先處理環境分流指出的相依／載入副作用，避免把這些目標納入模型成功率分母。
2. 先對原 `codellama:13b` 執行「測試連線」，查看三個角色資格。Auto 仍只使用各角色自身 verified 狀態；手動 Tier 是 best effort，不代表已取得資格。
3. 使用 `test/fixtures/python/lab_batch_manifest.json` 的五類樣本跑完整流程；為此輪建立新的結果目錄。先確認首次可執行、Reviewer completed、coverage/mutation 與 terminal status，再談速度。
4. 使用既有 scorecard，例（PowerShell）：

```powershell
.venv/Scripts/python.exe python_scripts/fixture_scorecard.py <結果根目錄> `
  --batch-manifest test/fixtures/python/lab_batch_manifest.json `
  --tier1-generation-mode llm-evidence-bound `
  --model-identity local/codellama:13b `
  --require-complete
```

失敗時讀 `run_manifest.json`、`role_events.jsonl`、`function_knowledge.json`、`final_report.md`。新增 `evidence-collection/static-ready.detail.retrieval` 可看 helper 選取量與省略量；`model-request` 記錄估計 input tokens、預算、contextWindow、Writer prompt 版本與 logical request 耗時；Reviewer `invalid-response.detail.diagnostics` 可直接分流。

`model-request/completed.elapsedMs` 含排隊、provider retry 和 format fallback，不能稱為純推論時間；requested 事件也是 logical request 數，不是底層 HTTP 次數。沒有這些欄位的舊報告記為未量測，不填零。Reviewer cache/suspension 規則保留，未完成審查仍是 incomplete。

五類通過後，再依相同環境、來源、Tier、角色 gate 與 context 預算，逐個評估 1B～5B 模型。另保留未出現在範例庫中的目標作測試，避免把記住範例當泛化能力。若要單獨量測 RAG 效益，再做相同 gates 下的「原語境／來源檢索／來源加範例」控制實驗；本次整合多項修復，前後差異不能全部歸因於 RAG。

## 本機證據與限制

回歸涵蓋真實 AST、Mock 正反例與五種範例執行、caller Trace 隔離、預算完整性、schema 拒絕回退，以及固定模型回覆搭配真實 Python、coverage、mutation 的 13B 能力設定整合測試。這些證明流程接線與防護，不是實際 13B 或 1B～5B 模型的通過率。

本機完整驗證為 Node 307、Python 118 通過；TypeScript、lint、建置、Webview 語法、tracked files／可達 Git 歷史密鑰掃描及 Git 差異格式檢查通過。

本機未找到 Ollama CLI，本輪未下載、啟動或測試實際模型；原批次及實驗室五類模型結果待 pull 後取得。長目標的必要證據仍可能超出小 context，這時明確停止，不能算相容性成功。

Ollama context 參數依據：[官方 FAQ](https://docs.ollama.com/faq)；schema 介面依據：[官方 Generate API](https://docs.ollama.com/api/generate)。
