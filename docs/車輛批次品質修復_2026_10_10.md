# 車輛批次品質修復

第一輪依據 `vehicle_manageme_2026_10_09_22_49`，第二輪再核對 `vehicle_manageme_2026_10_10_14_40`。以下分開保存各輪證據；不修改受測來源與歷史結果。

## 第二輪：14:40 批次與修復驗證

原批次涵蓋 212 個目標、836 次模型請求，耗時約 5 小時 37 分鐘。終態為 198 失敗、6 無突變候選、4 保留先前成果、3 審查受阻、1 完整通過。80 個目標停在提示預算、46 個停在候選驗證；7 個模組可載入，仍有 8 個目標在執行時缺少資源 schema。這些是不同階段的問題，不能全部歸因於環境或模型。

| 第二輪改動 | 可核對的行為 | 驗證界線 |
| --- | --- | --- |
| 精簡 Writer 語境 | 保留完整目標、必要 setup 與觀測；排除無關 import、重複規則，限制 optional 範例 | 不能截斷必要證據，也不提高輸入上限掩蓋問題 |
| AST 依賴物件形狀 | 明列來源實際使用的 receiver、方法回傳及 context-manager 層次；重綁與未知控制流保留診斷 | 只是 mock 建構提示，不是 expected、patch 授權或模型已遵守的證明 |
| 初始化 schema 規劃 | 追蹤可證明的本機 helper、設定 fallback 與明確欄位遷移，來源可定位的新 DB 納入預覽 | 不讀原設定／DB；空白 INI fixture 與 schema 需同次批准，跨來源摘要逐 worker 核對 |
| Reviewer 事實矛盾 | 同版執行／AST 事實反證 unbound import、已存在 mock assertion 與原樣替換斷言 | 只要求既有一次重審；不能刪除 finding 或直接授予批准 |
| 突變時限校準 | 成功 baseline 後採 `max(設定值, baseline 秒數 × 2 + 1)`；保存每筆分配 | 不延長 stage deadline；timeout／error 不計 killed，未完成仍無完整分數 |

同版應用的 8 個來源經靜態規劃得到 20 候選、去重後 18 個 schema 提案；3 個隔離 DB 各有 6 表。主版本及測試副本各 33 欄，舊備份 32 欄，差異來自明確的欄位遷移。3 個 fresh worker 各呼叫 4 個真實查詢，共 12 次成功；各 worker 都使用獨立空 DB 並完成清理。這證明來源支持的 schema 已可供查詢，不代表 AI 完整流程或整批品質通過。

使用保存的完整來源／觀測與目前規則重播提示：209 個可讀取語境的首次 Writer 請求全部在 6,000 token 預算內，中位數 3,326、最大 5,996；另 3 個目標沒有可用語境。96 個可重播修訂中仍有 1 個為 6,455 tokens，因完整 helper 證據不可裁切而保持拒絕。這是提示估量與完整區塊投影驗證，不是歷史請求的逐位元重建，也不是 209 個模型生成成功。首次生成的形狀圖若容不下，整份圖與圖例一起省略並明示依賴仍須從完整來源判讀；修訂保留完整契約。

實際模型檢查：F5 開發宿主可透過正式 SecretStorage 找到 `gemma-4-31b-it`；模型探索回傳 200 且列有 `generateContent`，但不含應用來源的最小生成請求在三次有限重試中均回傳 HTTP 500。沒有把金鑰或完整 provider 回應存入報告。Ollama 實際已安裝的 tag 為 `codegemma:2b`；模型名稱不作白名單，是否可用仍須以真實角色及執行證據判定。

小模型的服務 metadata 回報 3B／Q4_0，模板為補全／插入用途。固定中性案例中，一般指令曾重複提示或沒有產生測試；加入完整 setup 骨架及檔案起始提示的一次實驗產生完整測試，通過 target-aware 結構、Python AST 綁定、簽名及正式隔離執行，並確認實際進入原目標。沒有拼接模型程式碼、刪除定義或代寫斷言；尚無可重複成功率、Reviewer 或突變驗收證據。

這次實驗另揭露資格探針的真實缺口：呼叫目標後只做常數比較仍曾取得資格。已以結果來源／固定 expected 的連結修正，並升級 `python-unittest-v7` 使舊資格重新驗證。固定探針只接受模組層 TestCase 的直接方法，拒絕巢狀、同名覆寫與未執行範圍的斷言，runner 也要求非零實際案例數。規則原本允許的同值自含 fixture 是探針相容設計，與此缺口不同；正式候選仍不得重新定義目標。

正式 Ollama 請求另有傳輸缺口：本機模型的實際模板只讀 `.Prompt`，沒有讀 `.System`，原本分放在 `system` 的角色與輸出契約因此沒有進入模型。現在所有本機正式角色請求都把完整角色契約與使用者證據依原預算計算的相同順序放入 `prompt`，並以長度為 1 的空格 `system` 抑制 Modelfile 預設 SYSTEM 回填；仍使用模型原有模板，不切 `raw` 或覆寫模板，也沒有模型名稱分支。回歸核對文字只出現一次、完整來源未裁切、最終預算與實際送出內容相同；這證明指令可見性，不代表所有聊天模板的生成品質或角色優先序等價。既有連線／角色探針已將完整指示放在 `prompt`，沒有這次缺漏；探針仍可能繼承 Modelfile SYSTEM，資格與完整專案生成品質不能畫上等號。

上述 6,000 token 重播不是小模型的實際上限；本機 3B metadata 目前對應 5,000 context／3,500 input 預算。大型目標與完整隔離 schema 仍可能超額，不能用調高額度或切斷來源偽裝支援。下一階段若要繼續縮小提示，應依來源閉包選取相關資源，保留完整約束並預留格式補正空間。

修正前傳輸的本機全範圍驗收使用明確的 30 分鐘外層時限，保留原 8 檔／212 目標；截止時 178 失敗、1 取消、33 尚未開始。失敗為 109 Analyst 格式、67 提示預算及 2 AST 歧義；7 個可檢查模組全部載入，沒有環境預檢阻擋。232 次角色請求全部是 Analyst，231 完成、1 在取消時失敗；沒有進入 Writer、Reviewer 或突變。1154 筆資源生命週期全部確認清理，worker 暫存目錄為空，8 個來源與 2 個相依摘要保持不變。此批只能作舊傳輸 baseline，不代表修正後結果或整批完成。

修正後另用固定中性函式、相同真實 Trace 證據做最多兩次 Analyst 對照：舊請求未把四個必要 schema 欄位送入 `.Prompt`，回覆雖可解析但沒有有效策略／輸入提示；新請求完整傳入角色與證據，卻回傳非 JSON object，遭解析器拒絕。兩者 HTTP 200、無逾時。這證明傳輸缺漏已排除，尚未證明 `codegemma:2b` 能可靠完成 Analyst；不能將單次 Writer seed 成功外推為全角色或車輛專案通過。

## 第一輪改動與當時限制


| 原問題 | 修復 | 保留限制 |
| --- | --- | --- |
| 私有 helper 匯入、alias patch 與 connection/cursor mock 形狀錯誤 | Writer 明示來源使用點、明確 import 與回傳物件層次；增加中性真實執行回歸 | 提示不能保證模型一定遵守；仍須結構與執行驗證 |
| 修訂提示重複完整測試／來源，超額誤記 unknown | 完整相同片段改引用，修訂使用專用證據投影；統一由最終請求預算檢查記錄並停止 | 保留所有必要來源、setup、觀測與候選；不是所有提示都會更短，唯一必要證據太大仍停止 |
| Analyst 已回覆但 JSON 格式失敗 | 同一完整證據最多補正一次，共用原 deadline／目標預算 | API 失敗、取消、來源變動不觸發格式重問；再次失敗仍停止 |
| 已執行候選遭明確錯誤的 import／unused 指控 | Reviewer 使用同候選 AST import 與 binding 事實，機械矛盾交一次有界重審 | 不直接刪除 finding；未知語意或需求不由文字規則裁決；批准前不進突變 |
| SQLite 缺 schema 到函式執行才發現 | 初始化階段靜態解析支援的 literal DDL，精確配對已宣告資源後加入同次批准清單 | 不執行應用／SQL、不複製正式 DB；動態路徑與不完整 DDL 不猜測 |
| 突變 baseline 5 秒冷啟動逾時 | baseline 上限為每 mutant 上限與 20 秒的較大值，實際分配不超過 stage 剩餘時間 | 每 mutant 上限不增加；baseline 逾時不算 killed，也沒有有效分數 |

SQLite 提案限定 `CREATE TABLE IF NOT EXISTS`，避免預建後原初始化再次建表失敗。支援 column literal default、UNIQUE、INTEGER PRIMARY KEY AUTOINCREMENT 與複合 UNIQUE；工具從結構化設定重新建立，不直接執行來源 DDL。原有 schema／rows 不覆寫，衝突與未明確綁定來源的共享資源只列診斷。來源變更撤銷批准；每個 worker 建立新資料庫，原 DB 不變。

唯讀 AST 核對本機同版來源：8 個來源中有 6 個可靜態定位候選；另有 14 個動態 DB 路徑、2 個非 literal SQL 診斷。候選尚須與同來源的精確已宣告資源配對，這個數字不代表已套用 6 張表，也不代表原 8 個 schema 失敗目標已全部解除。

## 實驗室驗收

1. Pull 後重新 compile，再啟動 F5；確認報告中的建置時間已更新。
2. 先選少量純函式、資料庫與 UI 邊界目標。初始化預覽核對 `schema_plan.json` 的提案／診斷及精確資源；確認後只重檢一次。
3. 使用完整模式，核對同版候選的執行、Reviewer 與突變順序。逐輪流程及失敗報告現在有 baseline 上限、實際分配及耗時；最終報告保留既有精簡格式。
4. 仍失敗時提供該函式的 `run_manifest.json`、`role_events.jsonl`、`function_knowledge.json` 與 `failure_report.md`；資料庫提案問題再附初始化結果。不要貼 API key、正式資料或完整 provider 回應。
