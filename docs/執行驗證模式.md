# 完整品質驗證與執行診斷

正常測試預設使用 **完整品質驗證（含突變，預設）**，值為 `full`。候選須先通過結構、實際執行及同版本 Reviewer 審查，再進行覆蓋率與突變；測試生成失敗、環境受阻等情況不會直接執行突變。

舊版若已明確保存 `execution`，更新不會覆蓋設定；請在「驗證目標」切換成完整品質，之後保留此選擇。舊結果不能補標成已做突變，必須重新執行。

## 如何使用

1. 更新擴充功能後重新載入 VS Code／Extension Development Host。
2. 需要突變測試時，選 **完整品質驗證（含突變，預設）**。只有診斷生成測試的執行問題時才選 **僅執行驗證（不跑突變）**，設定鍵為 `llmUnitTest.validationMode=execution`；這不等於確認整個專案可運作。
3. 選擇受測專案，檔案選單預設 `all`；也可以只選單一程式及函式。
4. 使用相同 Python 檢查專案相依及模組初始化設定。缺套件、缺 API、mkdir／介面啟動受阻仍須修正環境或確認測試初始化替身；本模式不會放行外部操作或修改被測專題。
5. 事先角色資格檢查預設可選；開啟時需有同模型、端點及容量的 Writer 資格，關閉時可直接嘗試生成，不能把未測標為 verified。執行模式不啟動完整流程的 Tier 分流。
6. 開始測試，查看每個程式資料夾下的函式結果與 `final_report.md`。本機提交的測試不代表實驗室環境已通過，仍需在實驗室重跑。

## 驗證範圍

初次生成使用獨立的最小種子契約與 canonical import／class／方法外框，先請 AI 撰寫一個真實目標案例。外框沒有輸入或斷言答案。生成與修訂同時取得來源 Mock 工具確認的完整使用點名單，搭配既有 receiver／return 形狀契約；使用 `with patch(...)` 指引配合 `test_seed(self)` 外框，不另附要求 decorator 注入參數的第二份方法骨架。單純建立本地 Mock 不代表已替換模組相依，仍須由 AI 明確綁定與設定；指引不提供依賴值或答案，來源與相依版本須保持一致。無 Trace 時，來源支持的預期值仍是待實跑核驗的假說，不是已觀測事實或獨立需求規格。

本模式使用正式 Writer 的證據投影，保留完整來源、建構語境、globals、caller、相依來源及必要消費形狀；僅依 AST 分派規則，不請 Analyst 產生額外計畫。不再使用附有 `VALID_TEST_LINE_IDS` 審查指令的 Reviewer 證據文字作為生成提示，也不重複提供另一份種子外框。

Local 初次 Writer 的輸入預留與 wire 輸出 cap 成對，從1536 tokens開始，較小容量沿可用預留，既有較高 learned floor不降低；修訂依完整候選與實際工作量配置。截斷回覆仍不採用，原期限與有限恢復保持；這些數字不代表 Context 上限或要求模型輸出到上限。

初始 execution 草稿若尚無基線、也未嘗試原生執行，結構拒絕後可接續修正最新完整的未批准候選，避免第一項 import 修好後因第二項錯誤又遺失。`writer-draft/continued` 不是通過：草稿仍 rejected，executable／approved均為false，仍需完整驗證。full、修訂範圍拒絕、已有基線或首次 native 嘗試後，保留原回復政策與有限次數。

| 項目 | 執行驗證 | 完整品質驗證（full） |
| --- | --- | --- |
| AST、匯入預檢、初始化 fixture | 保留 | 保留 |
| 真實目標 binding、有效斷言、簽名、隔離執行 | 保留 | 保留 |
| 修復 | 沿用有限修訂與單方法範圍檢查 | 原完整流程 |
| 探索 Trace、語意規劃、coverage、突變與品質審查 | 延後，不計分 | 原完整流程與品質門檻 |
| 成功標示 | 執行驗證通過；完整品質尚未驗證 | 完整通過，或具體未完成／失敗原因 |

執行成功代表：這份測試含有真實目標的行為斷言，在目前來源、Python 及明確 Mock 設定下成功執行。它不代表整個應用能正式啟動、所有需求正確或所有分支已測到。執行證據必須重新取得，不能因為重用草稿就沿用舊的成功狀態。

## 如何避免假通過

- 候選先經 Python AST、目標 import／binding、Mock、函式簽名與有效斷言檢查。
- 正式 runner 必須確實觀察到目標原始 code frame，且有未略過、非 expectedFailure 的成功案例。
- runner 必須完整開始及結束隔離，沒有未處理或被吞掉的違規。
- 每次候選獨立保存 `execN_test.py`；`execution_baseline.json` 綁定 source／test hash、run ID、實際呼叫及隔離紀錄。批次再核對同一份證據。
- source 或已解析相依改變後證據失效；取消、缺報告、全略過與錯誤仍保持未通過。初次失敗及修復原因持續記錄。
- 既有完整品質政策不變。切換成 full 必須重跑，不能把 execution 的結果事後改標為完整通過。

## 環境與已知限制

執行模式不要求補裝 coverage／突變工具；完整品質模式仍會檢查它們。環境準備仍檢查必要套件及 `pip check`，不會自行降低被測專案的版本限制或假裝現有版本衝突已消失。模組初始化副作用仍由通用設定精靈依真實阻擋提出建議、預覽確認後重檢。

不做探索 Trace 後，測試依來源及明確控制的依賴提出可執行假設。資訊不足、模型輸出格式無效、初始化或建構方式不明仍可能失敗；工具保存原因，不猜測通過。模擬的 GUI／檔案／資料庫依賴不代表真正外部整合已驗證。Python 防護是本機程序內的防誤操作，不是抵禦惡意原生程式的作業系統沙箱。

## 重驗已保存的 AI 草稿

分析命令可明確傳入 `replayCandidate`，指定原結果資料夾 `directory`、角色事件 `sequence` 與候選原文 `codeHash`。只接受原本已完成模型回覆後保存的 Writer／Bug Fixer 候選，核對來源、精確目標及 provider／模型後原樣重新驗證，不讀取供應商完整回應，也不改寫測資或斷言。

預設同一 native 檔案且不再呼叫模型；若候選仍失敗會保存新的實際原因。明確指定 `repair: true` 才沿既有有限修訂呼叫模型。`allowIdenticalSource: true` 可把完整來源內容完全相同的另一份檔案所用的 AI 測試移轉為草稿；兩個目前檔案的完整 hash 都要一致，原環境、資源批准、Trace、執行與品質結果皆不移轉。

新的 `generationOrigin` 與 `candidate-replayed` 事件保留原始 run、sequence、code hash 及來源關係。成功仍須取得本次測試與來源 hash、實際 native 目標 frame 及完整隔離開始／結束證據。目前這個入口用於批次續跑，尚未新增側欄按鈕。

## 失敗後的參考計算與 helper 邊界

工具可解析簡單的 `hashlib` 摘要包裝與失敗測試中的 literal 輸入，交由宿主內建 crypto 計算標準參考。工具不匯入應用、不執行模型程式碼，也不直接替換斷言；AI 必須修改原測試，再由隔離執行驗證。證據記錄演算法、編碼及輸入摘要，不保存可逆的原始輸入位元組。未知運算、動態輸入或重綁保持不支援。

當 AttributeError 的 traceback 指向來源同檔、實際直接呼叫的唯一 helper，可向修復角色提供該使用點的 `with patch(...)` setup 指引。這只是測試隔離選項，既有來源綁定、禁止 patch 目標及實跑門檻仍會檢查；不把 traceback 文字當成 patch 授權，也不把整個 UI helper 圖都當成這個單元測試的目標。

## 小模型的來源片段修復指令

對唯一實測失敗方法的 dependency call 字串斷言，若原字串與同名來源呼叫的參數只差空白，可使用 `source-literal-argument-repair-v1`。工具以 AST 產生綁定來源／測試 hash 的候選片段與 UTF-8 位元組範圍；模型只回覆選取指令，例如 `REPLACE argument-1 WITH source-1`，避免在重寫整個方法時遺失換行。指令必須完整且只選已列出的來源片段，工具重新規劃並逐位元組核對後才套用；不接受模型自行新增程式碼。

這一步只可修改一個既有字串參數，其他輸入、setup、測試及斷言鎖定；不把來源回傳式當 oracle，也不提供新測資或業務預期。這個窄任務保留完整目標來源、失敗方法與全部片段選項，沒有修改資源配置的能力，因此不重複傳送隔離資源 schema。原請求期限、角色資格政策及計數保持。未知、歧義或非空白差異回到原修復流程。

工具只解析 AST，以 Python 隔離模式執行並使用 ASCII-safe JSON 保留中文內容，不匯入應用或執行模型程式碼。模型選取後的完整候選仍通過原修復範圍、綁定、真實目標呼叫與隔離執行；`literal-selection-applied` 只表示套用草稿，不能當成通過。事件保存原／新候選 hash、計畫 hash、片段 ID 與來源值摘要，沒有完整 provider 回應。

Mock receiver 亦可使用 `REPLACE receiver-1 WITH source-1`。候選只來自同一個既有明確 patch 的來源消費鏈，保留斷言方法、次數與參數。若是 AttributeError，須由唯一實測 test frame 的行號及完整原文證明錯在該斷言 receiver；目標或 setup 的例外不能套用。模型選取後仍須重新執行，不能為通過而降低呼叫次數要求。

獨立新建的標準 Mock 若被明確指定為 factory return value，可沿同一物件身分修復 receiver；配置必須唯一、未遭覆寫且在 target 呼叫前。來源已有其他 global 呼叫時，工具以完整模組 hash 與 AST 宣告補足名稱資訊，仍要求完整消費圖；整個模組不送入模型。對唯一方法內唯一可證明的結構差異由 Writer 處理，事件標記 `static-binding`，不宣稱已經發生 native 零呼叫失敗。

Checker 明確指出未綁定測試名稱時，Writer 可用 `INSERT import-1 FROM source-1` 選擇方法內 import。來源模組僅在工具內解析 AST、核對完整 hash 與唯一目標，不執行或整份送進模型；未知 helper 不猜，亦不安裝套件。同一來源的多個標準測試 helper 會由原 Checker 重掃確認，在同一行 import 一次補齊，避免中間結構失敗回復原稿後丟失前一項修訂。import 修正只消除名稱綁定問題，沒有核實資料形狀、預期值或業務正確性。
