## 即停修復的行為與界線

目前的原始結果顯示：`get_app_dir` 於 `14:38:14.899Z` 終局失敗，`_connect` 仍在 `14:38:15.307Z` 啟動。後續又執行其他目標，直到 `14:48:33.501Z` 使用者取消；第一個目標已失敗後仍等待約 10 分 18.602 秒。

證據：`get_app_dir` 的 `role_events.jsonl:65`；`_connect` 的同檔 `:1`；`batch_manifest.json:5`。

本次修復採以下順序：

1. **提早檢查共同 Auto 資格。** full／Auto 需要有效 Writer 與 Reviewer 資格；不符合時，在逐目標 Trace／生成前結束，明示缺少的角色與測試連線動作，不替每個函式重做相同失敗。
2. **首個目標終局失敗即停止批次。** 記錄第一個失敗目標、階段與原因；不再排程下一目標，剩餘目標明示未執行，不能偽裝為完成或通過。已產生的候選、執行證據與失敗報告保留。
3. **保留同一目標內有用途的修訂 loop。** 一個候選被拒絕後，依既有範圍與預算交 Writer／Bug Fixer 修訂，仍是原設計的一部分；「批次即停」不代表每個可修正候選錯誤都跳過修訂。目標已停止、預算耗盡或修訂無效形成終局失敗後，才停止整批。
4. **後續再解決生成瓶頸。** 先處理明確 import／骨架、mock 資料形狀與真實資源介面、無回傳函式的可驗證斷言，再量測較精簡 prompt 的耗時與成功率。此次不以放寬安全、品質、斷言或突變 gate 製造成功，也不調高 timeout 掩蓋排程問題。

## 小模型是否要求過高，以及下一次怎麼測

以這批證據，要求 3B 模型同時理解跨檔依賴、區分宿主資源說明、建立 DB mock、寫完整 unittest、修正失敗並通過所有品質 gate，難度確實高於短資格探針。模型漏 import、缺 assertion 及 fixture 形狀錯誤是已觀察到的能力缺口；然而 22:30 的零請求資格失敗、較大資料夾引入的載入副作用、晚阻擋及失敗後繼續排程，都屬系統流程問題，換更大模型也不會自動消失。

不再用 215／272 個目標整批試錯。先只選主檔，排除測試副本與備份，固定 3～5 個代表目標，例如 `get_app_dir`、`_now_text`、`_table_columns`、`_add_column_if_missing`、`init_db`。以同一來源雜湊、相同工具證據、相同安全／品質政策，對照 3B 與較大模型：

| 比較項目 | 判斷目的 |
| --- | --- |
| 有效角色資格與正式請求是否開始 | 排除流程先決條件，避免零請求誤判模型 |
| 目標 import／有效 assertion／mock shape 通過率 | 分辨工具契約與生成能力缺口 |
| 首次成功率、有效修訂率、重複候選率 | 評估是否需要更明確骨架或模型能力提升 |
| prefill／第一文字／decode／總耗時 | 分辨輸入負載與生成速度，不能只看 timeout 字樣 |
| 同一保留測試的覆蓋與完整突變量測 | 確認最終品質，不能只比較生成檔案數 |

較大模型是對照條件，不是保證成功的修復。若 3B 在精簡且可執行的契約下仍反覆產生同類錯誤，才據此界定小模型目前能支援的目標與需要加強的工具介面；不新增模型名稱白名單，也不降低通過標準。
