# 參數物件受控補測

此工具提供給 AI 的是已執行觀測，不是生成的正式測試。目的在於補足事件、頁面、控制項等物件參數無法由 scalar Trace 重播時的品質證據。

## 資料來源與執行

1. 正式 seed 通過執行與 Reviewer，完成第一輪 coverage／mutation。
2. Host 選取一個量測缺口，交付完整來源及保留的 AI 測試。
3. Python 只解析測試 AST。支援明確的 `types.SimpleNamespace`、`Mock(return_value=...)`、不依賴輸入的固定 factory，以及 `lambda x: x` 這類原樣回傳參數的配方；不執行模型測試或未知 helper。
4. 依來源讀取的屬性路徑規劃缺少、假值或受控 getter 例外。若焦點是 except 區塊，優先觀察其 try 區塊的讀取失敗；若為其他行，聚焦該行／條件，不複製整個專案。
5. 獨立 worker 重新推導允許的完整配方、核對來源及批准資源身份，建立新控制物件並呼叫真目標。只有目標確實進入、profile 完整、沒有副作用／ambient read且結果可重播，才回傳觀測。
6. Writer 取得一個完整案例，自行撰寫新增測試；Host 保留原基線，整份候選重新執行、審查並量測品質。

`namespace` 表示屬性物件；`factory` 每次產生一個新的固定回傳；`mock` 使用明確固定回傳；`identity` 返回實際傳入的同一參數。`faults` 覆蓋對指定屬性的讀取，拋出所列內建例外且無引數；沒有的屬性維持缺少。這些都是明確的測試控制，並非應用類別型別推斷。

## Writer 是否重放了同一種控制

Getter 拋例外與屬性值為None，即使令目標返回同一結果，也可能走不同分支。Host 現在保存與完整提示同時交付的案例，並在方法簽名前重申精確屬性與操作：`raise` 要在讀取屬性時拋出指定例外，`remove` 維持不存在，`false` 使用實際提供的None值。目標若捕捉例外而正常返回，測試應核對已觀測回傳，不能要求目標拋例外。提醒只提供宣告指引，body／assertion仍由AI撰寫。

合併後的 `--check-replay` 僅解析AST，排除目前基線方法，再比較新增方法的已知控制。明確把上述控制互換時，以 `fixture-replay-input-mismatch` 交Writer有限修訂；例如一般SimpleNamespace中的None值不能重放getter例外。自訂property類別等未知setup保留unknown，繼續正常執行與Reviewer；不是直接拒絕所有自訂物件，也不把unknown當matched。matched只核靜態配方，不能授予執行或品質通過。

末端也可附完整短摘要，並列其他參數屬性、factory／Mock／identity控制及同次實測回傳。它只格式化原typed資料，不計算新答案；getter的讀取覆寫與原完整封包的底層儲存配方分開說明。摘要超1500字元或無法完整表示時整段省略、引用原封包，不截斷其他控制來填滿Context。

`parameter-fixture-replay-v1` 綁定來源、候選、目前基線與觀測指紋；案例保留原seed provenance，可供同來源／模組／資源語境下後續增長的基線使用。核對不能借原基線方法冒充新案例，也不能把舊seed hash當目前基線hash。角色事件只保存固定狀態、原因碼與摘要，不保存provider原文。

若 Bug Fixer 修復後的完整基線還沒有 AST 方法盤點，補測會對該基線重新盤點，再決定新增名稱。原有方法、情境保留與同候選重新執行／審查仍須成立；盤點不是品質證據。

## 2026-10-24 真實小模型驗收快照

以下均使用本機 `qwen2.5-coder:3b-instruct`、原車輛來源及已批准的隔離資源，測試目標是 `main.py::get_plate_no_from_event`。AI 回覆來自真實模型；Checker、Reviewer、coverage 與 builtin 突變也實際執行。各次 seed 不同，不能據此宣稱固定幅度的通過率或速度提升。

| 執行目錄尾碼 | 結果與限制 |
| --- | --- |
| `Yc1I2L` | 新核對連續辨識出以 None 代替 getter 例外的候選；保留突變4/12，未達標。 |
| `Inu8tf` | 精確提醒後模型寫出 property，但遺漏其他控制，實跑不符觀測；保留突變7/12。 |
| `CXTus8` | 完整短摘要後曾達行14/14、突變11/12（91.67%），仍缺分支；第6輪因修復後基線缺 AST 盤點而中斷，終態 failed。此分數不是完整通過。 |
| `HlvU80` | 加入基線盤點修復後重跑，seed與3次新增均完成實跑／審查／突變；新增未減少缺口，因停滯結束。保留行10/14、突變7/12（58.33%），仍缺3條分支。 |

最後一次的具體錯誤是模型定義了會拋例外的 property 類別，卻把這個物件放進 `e.data`；讀取 `e.data` 只取出該物件，沒有讀取它的 property，因此未進入預期的 except 路徑。這種自訂類別包裝仍超出靜態解碼範圍，核對結果為 unknown；執行成功及 Reviewer 無 finding 不能證明控制已正確重放，最終 coverage 仍可揭露缺口。下一步應保守支援明確的測試自有 property 配方與精確 receiver 綁定，不能靠把 unknown 改成通過或放寬分支門檻處理。

已補回歸涵蓋：None／缺少／dict 的明確控制矛盾、unknown 不冒稱 matched、惡意 setup 不執行、來源／native 路徑／候選／增長基線身份，以及真實失敗→Bug Fixer→新基線 AST 盤點→錯誤補測拒絕→Writer 修訂→重跑重審突變。相關 Node 9項、Python14項與快速 Node745項／Python42項通過；集合有重疊，不相加。固定回覆整合不代替上述真模型結果；單函式結果不證明完整車輛批次已驗收，F5／DGX及完整開發回歸仍待驗。

## 時間、身分與報告

- 計畫最多四個候選，一輪只執行第一個尚未嘗試的案例。既有16秒工具階段集中供這一例冷載入及執行；外層20秒與原目標期限仍生效。
- source／seed hash、qualified target、模組實體路徑、批准資源 hash、完整配方及回覆 hash 都需一致。更名與缺口措辭不改變相同實驗指紋。
- `parameter-fixture-result-v1` 的 `observed` 僅表示取得受控觀測。缺少、受阻或不支援的案例不能成為預期值；觀測也不是獨立業務規格。
- 每輪保存 `loopN_parameter_fixture_experiments.json`；角色事件使用 `parameter-fixture-experiment`，保留狀態、指紋及固定原因碼。沒有完整 provider 回覆或可執行測試產物。
- 嘗試與提示交接分開記錄，未執行案例不算已嘗試，Context 不足時省略完整案例，不截斷配方或 typed value。

## 目前限制

自訂類別、共享或捕獲的物件身分、未知模組 setup、任意 lambda 計算、變動 import、async／generator 與不支援的變異位置都可能回覆 unsupported。這不是品質通過，也不改動突變分母。通過此工具的測試控制仍需由 AI 重現，並接受正式執行及審查；任何單一案例都不能證明整個車輛專案已完成驗收。
