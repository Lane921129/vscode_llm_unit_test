## 主要瓶頸與改善順序

1. **初始化一次彙整。** 純靜態 planner 先彙整可確定候選，掃描本身不 import；當目錄由配置或 helper 計算而留下 `dynamic-directory` 時，Host 先以既有已批准 fixtures 做一次受控匯入診斷，不暫套新提案，再將實測目錄建議與後續靜態入口合併為一次預覽、一次批准及一次批准後重檢。全程核對來源閉包，分開保存靜態候選與實測證據。這減少可辨識目錄與 GUI 入口被前一個錯誤遮住而必須再次操作的情況；未知副作用、無法解析的目錄或缺 schema 仍保留診斷，不承諾所有初始化都可自動解決。
2. **Writer 的依賴與測試契約。** 候選拒絕共有 713 個事件、涉及 161 個目標；結構拒絕 333/127、執行失敗 181/98、重複候選 122/76（事件/目標，分類可能重疊）。代表原因包括私有 helper 匯入錯誤、mock 受測目標、把字串當 connection、缺少有效目標行為斷言。下一輪應以來源使用點建立精簡依賴契約及真實重播案例，要求 AI 按一個具體錯誤增量修訂；保留真實目標與已通過案例，不放寬 gate。
3. **角色提示預算與分析師格式。** 26 個目標在 analyst-planning 格式失敗；28 個明確 prompt-budget，加上 5 個誤分 unknown 的完整修復證據超額，共 33 個預算相關停止。代表 Writer 需求 7,259 tokens、輸入預算 6,000、context 8,572。應先預估角色完整必要證據、保存超額原因及可用容量；縮減重複內容、選取完整相關證據區塊，不能截斷必要來源、亂擴 context 或依模型名稱豁免。
4. **資料庫執行前的明確 fixture。** 8 個 environment/resource-setup 目標都已通過模組載入，最後一次 invocation 的 observed=true，隔離完成事件為 resource-schema-required。這是函式執行後才缺 schema，與 import 失敗不同。下一步從明確 DDL／既有測試 fixture 收集 schema 提案，經一次預覽後在每個新 worker 重建；沒有明確 schema 就列出缺少項目，不猜表／欄位、不使用正式資料、不呼叫任意 init_db。
5. **Reviewer 與突變可用性。** 7 個已可執行候選遭審查阻擋，部分理由涉及正常 unittest import、wildcard import 或以註解充當 assertion evidence，需逐項以同候選事實核對並有界重審，不能直接刪 finding 當批准。4 個突變失敗是 baseline 的 5 秒時限、0 個 mutant 執行；下一步應分開記錄冷啟動、匯入與案例耗時，在既有總預算內分配 baseline 時限，超時仍不算 killed。

唯一有效突變為 `get_destination_minutes`：13 個全部執行，8 killed、5 survived，61.54%，低於 80%。`mutation/measured` 有 8 個目標，但其中 7 個是 no-candidates，不能當成 8 個有效分數。該唯一有效成果的 knowledge 狀態仍為 not-measured，而保留測試與原始 mutation 報告身份一致；後續應分清「最新候選狀態」與「保留基線量測」並修正摘要分類。

## 可重播驗收順序

先用中性 fixture 分別驗證兩條路徑：「靜態目錄需求在前、GUI 入口在後、相依檔沒有函式」可在未 import 前一次預覽；「配置或 helper 算目錄」先做一次只含既有批准設定的受控診斷，再把實測目錄與靜態入口合併預覽。兩者批准後都只重檢一次。取消靜態預覽時不 import；取消動態目錄預覽時可能已完成初次診斷，但不套用任何新提案、不進行批准後重檢。來源變更不套用，實際新障礙停止且不循環，也要驗證未知副作用保持受阻。再於實驗室先跑純函式、資料庫 mock、UI 邊界各少量目標，分別核對執行、Reviewer 與完整突變，最後才重跑整批。
